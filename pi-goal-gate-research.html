Does /goal actually work?

A Claude-Code-style autonomous completion gate for the Pi coding harness — set a condition, walk away, and it keeps nudging the model until a real, independently-verifiable pass backs a genuine completion claim. Three live trials, two real bugs found and fixed in the first one, and one gap that's still open after all three.

What /goal is

Most autonomous-agent failures aren't the model refusing to work — they're the model believing it's done when it isn't. /goal <condition> sets a goal for the rest of a Pi session. On every turn that looks like a stopping point, a gate checks whether the model has actually earned the right to stop: its final message must end with a GOAL COMPLETE: <evidence> line, and the most recent broad verification command run since then must have genuinely passed. Absent either, it nudges the model to keep working instead of letting the turn — and, unattended, the process — end.

Deliberately not built: an LLM judging its own completion. A same-model judge carries the same self-report bias the gate exists to route around. The one signal trusted here is a verification command that was actually run and actually passed — the same convention the rest of this harness already uses.

Three live trials

TRIAL 1 Fresh empty repo — Go "print hello" 2026-08-09

The smallest possible smoke test surfaced two real, unrelated bugs on first contact — exactly the value of running something live instead of trusting the source.

bug found The kickoff never ran at all. pi -p "/goal ..." exited immediately — zero agent_start events, not even one attempted turn. sendUserMessage() only queues a turn; it doesn't return a promise, so waitForIdle() called right after it raced the not-yet-started turn and returned instantly. Fixed by waiting for a real agent_start event first.
bug found A genuine pass kept getting rejected. After the kickoff fix, the same task ran 74+ turns across 15 nudge rounds without ever accepting a GOAL COMPLETE claim — despite the verification command visibly passing. Cause: the pass/fail signal was reset on every nudge, including ordinary mid-task narrative with no tool call attached, wiping out real passes long before the model's next genuine attempt. Fixed to reset only when a claim is specifically rejected.
confirmed Rerun of the identical task after both fixes: accepted on the model's first claim, 11 turns instead of 74+. Verified independently, outside the harness — make verify passes, the program actually prints hello.
TRIAL 2 Fresh empty repo — Python calculator + pytest 2026-08-09/10

A second stack, to see whether the fixes generalized rather than papering over one specific run.

confirmed Kickoff fired immediately, no race — holds on a second stack.
confirmed The model hit real environment friction first — no venv, pytest not installed, two genuine verification failures — and only claimed complete once tests actually passed. Independently rerun afterward: 5/5 passed, matching the claim exactly.
correction This trial's GOAL COMPLETE landed on the model's very first attempt (no preceding nudge), so it never actually exercised the reset-on-nudge code path Trial 1's second bug lived in — an earlier draft of this write-up claimed otherwise and overstated it. Caught on review, corrected against the raw trace rather than left as-is.
confirmed Bonus: a second, independent mechanism — the artifact guard — caught real leftover binaries in .venv/ after the goal cleared, and nudged its own cleanup turn without interfering with the (already-settled) goal state.
TRIAL 3 Real app — wire delete/export/rename into the UI 2026-08-10

Not a synthetic task this time: the actual leftover scope from an earlier build, run foreground against a real, existing Go+Flutter app.

still open Converged on the first genuine attempt again — third straight trial that hasn't exercised the reject-and-retry path. Every trial so far has happened to get it right the first time.
confirmed New signal: after the goal was accepted, an independent reviewer caught a real crash bug — .first on a list that could legitimately be empty — and drove its own three-round fix cycle the gate's own pass/fail signal couldn't have seen on its own.
gap flagged The run made zero git commits despite tests passing throughout — accepting a goal doesn't imply the work got committed. Verified the diff independently, then committed and pushed it by hand.
Methodology note. Every claim above was re-checked against the raw --mode json event log and, where possible, against the repository itself afterward — not taken from the model's own end-of-run summary. One overclaim (Trial 2's correction, above) only surfaced this way.

What this leaves open

  • The reject-and-nudge loop itself is still unconfirmed live. All three trials converged on the model's first genuine completion attempt. The mechanism that rejects a false claim and successfully drives a real correction round has only been proven in principle (Trial 1's before/after fix), never watched happen end-to-end on a task that doesn't get it right the first time.
  • Unattended, multi-restart endurance is unproven. A separate run this session was killed twice, unexplained, mid-round — recovery each time was a human noticing and manually resuming, not the live goal state surviving a restart on its own (it's deliberately session-scoped, not persisted to disk).
  • Completion doesn't imply commit. Trial 3's real, verified work sat uncommitted until checked and pushed by hand.
