Qwen3.8-27B: from 0/4 to 4/4

A local Qwen3.8-27B route was consistently landing the wrong fix on a controlled Go task, then never converting its own correct diagnosis into a code change. Three default settings turned out to be responsible — finding and fixing them flipped the result.

What was happening

Every one of four earlier trials produced the exact same bug: the eviction logic confused a cache value for a cache key, deleting the wrong (or a nonexistent) map entry. An independent reviewer model caught the bug correctly all four times. The primary model never acted on it — instead it re-verified its own diagnosis over and over, in one case for 26 minutes straight, without ever landing the one-line fix it had already found.

That gap — correct diagnosis, no follow-through — is the thing this investigation chased down.

Two root causes, both config defaults

Cause 1

Thinking was silently off

Qwen3.8-27B is a hybrid-reasoning model — it's meant to think before answering. The harness's model entry had reasoning: false, which suppressed every thinking-control field the client would otherwise send. Not an explicit "off" — an unset one, discovered only by checking what the server actually returned.

Cause 2

Requests ran fully greedy

The harness has no temperature setting anywhere — no CLI flag, no config field. The inference server defaults to temperature 0 (greedy decoding) whenever it's omitted, and it separately ignores the model's own recommended defaults. Every trial, including the first four, ran deterministic greedy decode on what's meant to be a temperature-1.0 reasoning model.

A third bug appeared the moment we fixed the first one. Turning thinking on has a side effect on generic OpenAI-compatible endpoints: the client switches the system prompt from role "system" to role "developer". This server's tokenizer rejects that role outright — every turn failed with a 503, burning all retries, and the trial ended with zero code changes, worse than doing nothing. Caught immediately by checking the run's own transcript rather than assuming the fix had worked, and fixed with one explicit config flag.

What changed

Before

defaultThinkingLevel: "off"

After
reasoning: true
compat.thinkingFormat: "qwen"
compat.supportsDeveloperRole: false
defaultThinkingLevel: "medium"
temperature: 0.6
top_p: 0.95
top_k: 20
presence_penalty: 0.0 (all injected client-side)
Sampling params, 2026-08-19: the temperature-only fix above left top_p/top_k/presence_penalty at whatever the inference server defaults to when a request omits them. A pass of vendor and community research (Qwen's own model card, Unsloth's run guide) turned up a documented "precise coding" preset for this model — distinct from both its general thinking default and its non-thinking instruct default — and confirmed temperature: 0.6 was already the vendor's own coding-specific value, not just an analogy carried over from the prior checkpoint. The client-side injection hook now sets the full preset (temperature 0.6, top_p 0.95, top_k 20, presence_penalty 0.0). Not yet re-validated against a live battery run — treat as a config change pending confirmation, the same way the temperature fix itself was validated before being called settled.

Broader battery (2026-08-17): quality held, reliability didn't

With the fix replicated on one repeated task, the next question was whether it held across the wider multi-stack suite the harness's original nine-pair baseline-vs-harness battery already covered. Reran it (same seed, same task pool minus go/lru-cache — already separately proven) at the hardened config: 7 pairs, stock Pi vs. the installed harness.

ArmValid runsPassedNotes
Baseline7 / 77 / 7Every run completed and passed.
Harness (hardened)4 / 74 / 4 of validEvery run that finished passed — the gap is completion, not correctness.

Median paired runtime overhead on the four fully-valid pairs was ~312%, up from 100.3% pre-hardening — the expected cost of thinking-enabled turns. The real, actionable finding: 3 of 7 harness arms (43%) didn't finish inside per-task timeout budgets that were sized before thinking was turned on and haven't been revisited since. Two were genuine timeouts (one had already produced a hidden-test-passing fix before running out the clock — a pure settlement-speed problem, not a wrong answer); one was a real, now-fixed extension bug (git-checkpoint.ts crashed on a documented Pi stale-context error two sibling extensions already guarded against — added the same guard, 4 new tests, full 179-test suite green). Full record: pi/evals/hardened-screening-2026-08-17.json.
