## Learnings

1. **Three of 12 real tickets were unfair** — not model failures:
   - `aistack-models-hide-offline`: hidden tests over-constrain the
     implementation (`session.get(url)` must take exactly one argument;
     fake response has no `.read()`); both arms wrote sensible code with a
     timeout and failed.
   - `pa-note-create-idempotent`: hidden tests require last-write-wins
     upsert without a second create call; the spec only said "no
     duplicate" and "deterministic".
   - `pa-shared-reminder-rules`: hidden test requires stripping `Position`
     on recipient updates; never stated in the spec.
   Cause: one-line specs written from commit messages miss requirements
   that live only in the tests. **Validates the plan's oracle self-check:**
   two independent implementations failing identically is the signal that
   the oracle, not the code, is wrong.
2. **Spec contradictions halt the harness, not stock pi.** The first spec
   template ("do not modify existing tests") contradicted a ticket whose fix
   edits an existing test; the harness's karpathy guardrail correctly
   stopped and explained the conflict, stock pi pushed through. Fixed in
   the template; implication: Claude's planning output needs a
   contradiction check before unattended execution.
3. **Memory aborts masqueraded as quality failures.** mtplx's guard aborted
   prefills ("insufficient memory … macOS compressed N GiB") in 8 of the
   first 68 runs; every harness abort ended in failure (4/4), stock pi 2/4.
   Raw numbers made the harness look worse (79% vs 86%); excluding aborts
   the arms tie. Detection must read pi's output (the abort is surfaced
   there), not only `mtplx.log`.
4. **The proxy's mtplx idle-clear has been a no-op** since the 2.12 swap:
   log lines show identical bytes before/after (e.g. 62.2 → 62.2 GB) and a
   manual `/admin/cache/clear` returns `mlx_cache_cleanup: model_lock_busy`
   during load. Qwen grew 41 → 62 GB overnight. A relief loop (clear when
   footprint > 52 GB or free < 25%, retry while busy) holds it near 47 GB.
5. **The harness adds time without adding passes on this battery** (~1.1×
   here; 1–3× in August), and its review/quality findings are report-only
   since 2026-08-19, so they cannot convert a failing run into a passing
   one. Correction has to move outside the session (gate-driven repair
   rounds, best-of-N) — plan Phases 4–5.
6. **Ticket size shows up as timeouts:** `sf-runner-changed-files` times out
   at 30 min in both arms — the ≤150-line micro-ticket rule exists for this.
7. **SSD session tier is write-only for batch evals:** ~37 GB written in the
   first 1.5 h with 1 restore — every task is a fresh session.
